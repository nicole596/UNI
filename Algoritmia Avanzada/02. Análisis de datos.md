## ¿Por qué es necesario analizar la complejidad?

En la vida real, para poder comparar la eficiencia de diferentes algoritmos solo comparando el tiempo de ejecución y el de compilación, seria estrictamente necesario compararlos en el mismo dispositivos y en condiciones controladas. Sin embargo no siempre se pueden tener esas condiciones, por lo que es necesario encontrar una manera de compararlos independientemente del dispositivo en el que se ejecuten.

## ¿Qué es el espacio de complejidad?

Son los espacios de almacenamiento o memoria  RAM que necesita un algoritmo.

 ![[Pasted image 20260921114929.png]]

- **Notación Big-O (O):** Modela el **cota superior** (_Upper Bound_) del tiempo de ejecución. Describe el peor escenario posible: $$T(n) \le c \cdot f(n) \implies T(n) = O(f(n)).$$
- **Notación Big-\Omega (\Omega):** Modela la **cota inferior** (_Lower Bound_) o el mejor escenario posible: $$T(n) \ge c \cdot g(n) \implies T(n) = \Omega(g(n)).$$
- ​**Notación Big-\Theta(\Theta):** Representa un **ajuste estricto** (_Tight Bound_), donde el comportamiento del algoritmo está acotado tanto por arriba como por abajo por la misma función.

#### Complejidades Comunes y Rendimiento
- **Constante (c):** El tiempo no depende del tamaño de entrada N.
- **Logarítmica (\log N):** Típica en algoritmos que dividen el problema a la mitad en cada paso (ej. Búsqueda binaria, bucles con i /= 2).
- **Lineal (N):** Crece proporcionalmente al tamaño del insumo (ej. bucle `for` tradicional con saltos constantes i - 4).
- **Cuadrática (N^2) / Cúbica (N^3):** Típica en bucles anidados.
- **Exponencial (2^N):** Crece explosivamente; ineficiente para valores grandes de N. 

### Funciones Recursivas e Iterativas

1. **Casos Base (_Base Cases_):** Casos simples que se resuelven de forma directa sin llamar de nuevo a la función para detener la recursión.
2. **Progreso (_Making Progress_):** Cada llamada recursiva debe acercarse progresivamente al caso base.
3. **Regla de Diseño (_Design Rule_):** Asumir que todas las llamadas recursivas internas funcionan correctamente.
4. **Regla del Interés Compuesto (_Compound Interest Rule_):** Evitar resolver el mismo sub problema múltiples veces en llamadas recursivas separadas para no degrada la complejidad a niveles exponenciales.
``` C++
#include <iostream>
#include <random>
#include <chrono>

using namespace std;

static long long sumaMatrix(const int matrix[], int n) {
    long long sum = 0;
    for ( int i =0; i < n; i++) {
        sum += matrix[i];
    }
    return sum;
}

int main() { 

    std::cout << "Big O Notation!" << std::endl;
    int size_of_n[] = {1000, 2000, 3000, 4000, 5000, 6000, 7000, 8000, 9000, 10000};
    const int SIZE_OF_N = sizeof(size_of_n) / sizeof(int);

    //Random number generador

    random_device rd;
    mt19937 generador(rd());
    uniform_int_distribution<> distribution(1, 100);
    const int N_EJECUCIONES = 20;
    for (int i = 0; i<SIZE_OF_N; i++) {
        int n = size_of_n[i];
        // array de n elementos
        int* matrix = new int[n];
        // llenar cada array
        for (int j = 0; j < n; j++) {
            matrix[j] = distribution(generador);
        }
        double totalTime = 0.0;
        long long resultado = 0;
        for (int j = 0; j < N_EJECUCIONES; j++) {
            auto  initialTime = chrono::high_resolution_clock::now();
            resultado = sumaMatrix(matrix, n);
            auto endTime = chrono::high_resolution_clock::now();
            double diffTime = chrono::duration<double, micro>(endTime - initialTime).count();
            totalTime += diffTime;
        }
        // tiempo promedio
        double averageTime = totalTime / N_EJECUCIONES;
        cout<< averageTime << ", ";
        delete [] matrix;
    }


    cout << " done !!!" << endl;
    return 0;
}
```
